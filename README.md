## 프로젝트 개요

본 프로젝트는 팀즈(Microsoft Teams)에서 오가는 비정형 자연어 대화—채팅, 파일, 게시글—를 실시간으로 수집하고, AI 에이전트가 이를 **온톨로지(Ontology) 기반의 구조화된 지식 그래프**로 변환하는 프로젝트 관리 시스템입니다.

단순한 요약 도구가 아닙니다. 대화 속에 숨어 있는 **의사결정, 업무 배분, 일정, 이슈**를 추출하고 분류하여 Git 레포지토리에 버전 관리되는 Markdown 문서로 영속화합니다. 그 결과물은 언제든 질의할 수 있는 **살아 있는 프로젝트 기억**이 됩니다.

```
각종 비정형 데이터 (팀즈 채팅, 보고 문서, 개발 내역 등) ──▶ 에이전트 서버 ──▶ 온톨로지
                                                                          │
                                                주간보고 ◀── 조회 / 분석 / 알림
```

> "구조화된 입력만 받는 도구들, 느린 실시간성, 어려운 이력 추적 — 이 세 가지를 한 번에 해결하는 것은 AI뿐이다."

매일 수백 개의 메시지가 오가는 프로젝트 현장에서, 정작 **"무슨 결정이 언제 왜 내려졌는지"** 를 아는 사람은 없습니다. 팀원이 바뀌면 컨텍스트는 사라지고, 신규 합류자는 수백 개의 채팅 로그를 뒤져야 합니다.

전지적 팀즈 시점은 이 문제를 근본부터 해결합니다. 팀원은 여전히 팀즈에서 자연스럽게 대화하면 됩니다. 나머지는 에이전트가 합니다.

**프로젝트의 모든 기억은 사라지지 않습니다.**

## 문제 인식

### 현장에서 반복되는 고통

많은 팀에서 업무마다 채팅방을 만듭니다. 기능 하나당 채팅방 하나, 이슈 하나당 채팅방 하나. 어느새 수십 개의 채팅방이 쌓이고, 정작 중요한 결정사항은 스크롤 저 아래에 묻혀 버립니다.

| 증상 | 원인 |
|---|---|
| "그 파일 어디 있어요?" | 파일 저장 위치가 사람마다 다르고 비슷한 문서가 각기 다른 폴더에 산재 |
| "그때 어떻게 결정했더라?" | 의사결정 이력이 채팅 로그에만 존재, 검색 불가 |
| "제가 그 채팅방 없는데요" | 컨텍스트가 채팅방 단위로 파편화, 합류 후 온보딩 불가 |
| 일정 충돌 | 서로 다른 채팅방에서 같은 시간대 일정이 잡혀도 인지 불가 |

### 기존 프로젝트 관리 도구의 한계

- **구조화된 입력만 수용**: Jira, Notion 등은 사람이 직접 정보를 입력해야 하는 구조. 현업의 바쁜 환경에서 이 비용은 대부분 후순위로 밀림.
- **실시간성 부재**: 회의 후 별도로 문서를 작성해야 하는 이중 작업.
- **이력 관리의 부재**: 과거에 어떤 결정이 왜 내려졌는지 추적 불가.

### 팀즈를 계속 쓰는 이유

팀원들이 팀즈를 떠나지 않는 데는 이유가 있습니다.

- **익숙함**: 자연어로 소통하는 것은 인간에게 가장 낮은 마찰의 커뮤니케이션 방식.
- **신속성**: 실시간으로 상대방의 상태를 확인하고 정보를 나눌 수 있음.
- **보편성**: 모두가 이미 사용 중. 새 도구 도입의 학습 비용이 없음.

**결론**: 도구를 바꾸는 것이 아니라, 기존 커뮤니케이션 흐름 위에 인텔리전스 레이어를 얹어야 합니다.

## 해결 전략

> "구조화되지 않은 입력으로부터 기록·분류·분석·산출하는 것은 오직 AI만이 가능하다."

팀즈의 **익숙함·신속성·보편성**을 그대로 유지하면서, 백그라운드에서 AI 에이전트가 다음을 수행합니다.

```
채팅/파일/게시글 수신
       │
       ▼
  의도 파악 에이전트
       │
  ┌────┴─────┐
  │          │
  ▼          ▼
정보 조작   정보 조회
에이전트    에이전트
  │
  ▼
온톨로지 업데이트 (Git Commit)
  │
  ▼
주간보고 제작 에이전트
```

채팅 한 줄이 프로젝트 지식 그래프의 노드가 되고, 모든 변경은 Git 커밋으로 영속화됩니다.

## 시스템 아키텍처

### 데이터 흐름

```
[Microsoft Teams]
        │ 메시지 발생
        ▼
[Power Automate]
        │ Webhook / REST API
        ▼
[Python 에이전트 서버]
        │
   ┌────┴──────────────┐
   │                   │
   ▼                   ▼
[LLM 호출]       [메시지 큐 (SQS)]
   │                   │ 배치 처리
   ▼                   ▼
[온톨로지 조회]  [배치 처리기]
   │
   ├── Git 레포지토리 (MD 파일, 현재 상태)
   ├── Qdrant 벡터 DB (헤더 + 트리 구조, Graph RAG)
   └── RDBMS (장기 커밋 이력, 태그, 날짜)
```

### 메시지 처리 단위 전략

단일 메시지만으로는 의도를 파악하기 어렵습니다. 다음 옵션 중 채팅방 특성에 따라 배치 단위를 유연하게 설정합니다.

| 처리 단위 | 특징 | 적합한 상황 |
|---|---|---|
| 읽음 처리된 묶음 | 자연스러운 대화 흐름 보존 | 일반 업무 채팅 |
| 멘션 + 답장 단위 | 핵심 의사결정 집중 처리 | 결정이 필요한 스레드 |
| 1시간 단위 배치 | 일정한 주기로 처리 | 활발한 채팅방 |
| 커스텀 배치 | 톡방 특성에 맞게 설정 | 특수 목적 채팅방 |

## 온톨로지 설계

### 폴더 구조

최대 **3 depth**까지만 분류합니다. 너무 깊으면 찾기 어렵고, 너무 얕으면 섞입니다.

```
📁 프로젝트 온톨로지
├── 00_BASE/          # 프로젝트 기준 정보, 용어 정의
│   └── ***.md
├── 01_PERSON/        # 구성원 정보, 역할, 업무 이력
│   ├── AAA.md
│   └── BBB.md
├── 02_ORGANIZATION/  # 조직 구조, 팀 정보
├── 03_BUSINESS/      # 비즈니스 규칙, 정책, 의사결정 이력
└── 04_WBS/           # 업무 분류 체계, 기능별 상세
    └── 로봇목록출력기능.md
```

### MD 파일 구조 원칙

- **바디**: 최신 정보만 유지. 현재 상태의 단일 진실 공급원(Single Source of Truth).
- **히스토리**: Git blame 또는 별도 히스토리 섹션으로 관리.
- **커밋 규칙**: 육하원칙(누가/무엇을/언제/어디서/왜/어떻게) 중 하나라도 바뀌면 별도 커밋으로 기록.
- **미완성 정보**: 추가 정보가 필요한 필드는 `보충필요` 태그로 표시.

### 메타데이터 구조

Palantir 온톨로지 구축 사례를 참고한 메타데이터 설계:

```markdown
---
id: feature/robot-list-print
type: WBS
owner: BBB
created_by: AAA
created_at: 2026-04-30
due_date: 2026-04-30
status: in_progress
tags: [robot, feature, backend]
related: [01_PERSON/BBB.md, 03_BUSINESS/robot-policy.md]
---
```

### 저장소별 역할 분리

| 저장소 | 저장 내용 | 특징 |
|---|---|---|
| **Git 레포지토리** | MD 파일 전체 (현재 상태) | 버전 관리, diff/blame 지원 |
| **Qdrant (벡터 DB)** | MD 파일 헤더 + 트리 구조 (바디 제외), 비정형 문서(PPT/PDF) | 의미 검색, Graph RAG |
| **RDBMS** | 커밋 ID, 태그, 날짜, 장기 이력 | 1년 이상 과거 데이터 쿼리 |

## 에이전트 구성

### 1. 의도 파악 에이전트 (Orchestrator)

수신한 대화 내용을 분석하여 어떤 서브에이전트를 호출할지 결정합니다.

```
입력: 팀즈 채팅 묶음
출력: 이벤트 타입 분류
  - NEW_TASK: 신규 업무 발생
  - UPDATE_TASK: 기존 업무 변경
  - ISSUE: 이슈 발생
  - QUERY: 정보 조회 요청
  - REPORT: 보고서 생성 요청
  - SCHEDULE: 일정 등록/변경
```

### 2. 정보 조작 에이전트 (CRUD Agent)

온톨로지에 실제 변경을 가합니다.

```
[신규 업무]
  1. GraphRAG에서 관련 컨텍스트 탐색
  2. 관련 정보 없음 → 신규 파일 생성
  3. 빈 필드는 "보충필요" 표시

[기존 업무 업데이트]
  1. 기존 온톨로지 파일 수정
  2. 변경된 필드만 업데이트

[커밋]
  $ git add .
  $ git commit -m "Add and allocate [기능명] task to [담당자], by [지시자]"
```

### 3. 정보 조회 에이전트 (Query Agent)

과거 이력과 현재 상태를 검색합니다.

| 조회 유형 | 예시 질문 | 사용 도구 |
|---|---|---|
| **토픽 조회** | "로봇 목록 기능 개발 히스토리 알려줘" | Graph RAG + git blame |
| **날짜 범위 조회** | "이번 주 작업 내역 보여줘" | git log (날짜 필터) |
| **사람 조회** | "BBB씨 이번 달 업무 이력은?" | git log --author + RAG |
| **결정사항 조회** | "A 안건 어떻게 결정됐더라?" | git log -p + RDBMS |

#### 이력 조회 깊이별 전략

```
최근 1년 이내   → $ git blame [파일]
1년 이내 상세   → $ git log -p -- [파일]
1년 이상 과거   → RDBMS 쿼리
```

### 4. 주간보고 제작 에이전트 (Report Agent)

특정 기간·주제에 대한 정보를 수집하여 보기 좋은 형식으로 가공합니다.

```
입력: "이번 주 작업 내역을 종합해서 보고서 md 파일로 만들어 줘"

처리:
  1. 20260420 ~ 20260424 커밋 전체 탐색 (git log)
  2. 변경된 파일별 diff 분석
  3. 담당자별 업무 집계
  4. 발생한 이슈 목록 추출
  5. 차주 예정 업무 추출

출력:
  - 금주 진행 상황 (기능별)
  - 발생 이슈 목록
  - 차주 할 일
  - 커밋 기록 링크
```

### 에이전트 도구 (Tools)

```python
tools = [
    BashTool(),          # 파일 시스템 조회, git 명령
    SPARQLQueryTool(),   # 그래프 DB 온톨로지 쿼리
    GraphRAGSearchTool() # 벡터 DB 의미 기반 검색
]
```

## 변경사항 이력 관리

### 단기 기억 vs 장기 기억

```
현재 ──────────────────────────────────────── 과거
  │           1년 기준            │
  ▼                               ▼
Git blame               RDBMS (연말 배치 이관)
(실시간 추적)           (커밋 ID, 태그, 날짜)
```

### 커밋 태그 규칙

커밋 메시지에 시맨틱 태그를 추가하여 후속 쿼리를 용이하게 합니다.

```bash
# 예시
git commit -m "[ASSIGN] 로봇목록출력 기능을 BBB에게 할당, by AAA"
git commit -m "[REASSIGN] 로봇목록출력 담당자 BBB → CCC 변경"
git commit -m "[ISSUE] 비용 이슈 발생 - 로봇목록출력 기능"
git commit -m "[RESOLVE] 비용 이슈 해결 - 예산 승인 완료"
```

### 미래 일정 관리 및 알림

- **개인 plan MD 파일** ↔ **일정 MD 파일** 상호 참조
- Power Automate 날짜 트리거로 리마인드 알림 전송
- 사용자 MD 파일에 `state: pending | in_progress | done` 상태 관리
- 배포 요청, 검토 요청 등 망각 위험 항목 자동 리마인드

## 실제 시나리오

### 시나리오 1: 신규 업무 발생

```
팀즈 채팅:
AAA: "아 생각해보니 로봇 목록을 출력하는 기능 만들어야 하는데
      이 부분 BBB씨가 맡아 주세요. 30일까지"
BBB: "어 그런데 비용 이슈가 있어서 ~하게 변경해야 합니다"
```

**에이전트 처리 흐름:**

```
1. 의도 파악: NEW_TASK + ISSUE 복합 이벤트

2. GraphRAG 탐색
   → "로봇 목록 출력 기능" 관련 기존 컨텍스트 없음
   → 신규 업무로 분류

3. 파일 생성/수정
   📄 04_WBS/로봇목록출력기능.md  (신규 생성)
   📄 01_PERSON/AAA.md           (업무 지시 이력 추가)
   📄 01_PERSON/BBB.md           (담당 업무 추가)

4. Git 커밋
   $ git add .
   $ git commit -m "[ASSIGN] Add Robot List print feature, assigned to BBB by AAA, due 2026-04-30"

5. 이슈 별도 기록
   📄 05_ISSUE/로봇목록비용이슈.md  (이슈 폴더 관리)
   → 04_WBS/로봇목록출력기능.md 와 관계형 연결
```

### 시나리오 2: 과거 이력 조회

```
팀원: "그때 로봇 목록 출력 기능 누가 누구한테 개발하라고 시켰더라?"
```

**에이전트 처리 흐름:**

```
1. 의도 파악: QUERY → 담당자 변경 이력 조회

2. GraphRAG 검색
   → "로봇 목록 출력 기능" → 04_WBS/로봇목록출력기능.md 탐색

3. Git 이력 조회
   $ git blame 04_WBS/로봇목록출력기능.md
   → 담당자 필드 최초 커밋: "BBB, by AAA, 2026-04-14"

4. 결과 반환
   "2026-04-14, AAA님이 BBB님께 '로봇 목록 출력 기능' 개발을 요청했습니다.
    마감: 2026-04-30 / 관련 이슈: 로봇목록비용이슈"
```
